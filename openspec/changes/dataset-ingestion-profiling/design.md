# Design: Dataset Ingestion and Profiling Pipeline

## Technical Approach

The design transforms the procedural scripts found in the prototype (`create_manifest.py` and `profile_data.py`) into a modular, testable, and robust **Clean Architecture** implementation in Python.

The architecture isolates the core domain entities from I/O mechanisms, providing:
1. Pure domain entities for manifest records and statistical summaries.
2. Independent use cases for dataset verification, manifest generation, and statistical profiling.
3. Decoupled file adapters with resilient root resolution (`pathlib.Path`).
4. A unified CLI interface (`ml_service/src/cli.py`) that eliminates manual path navigation.

---

## Architecture Decisions

### Decision: Clean Architecture Layering in Python (`ml_service/src/`)
- **Choice:** Separate code into `domain/` (entities/dataclasses), `ingestion/` (ingestion use cases), `profiling/` (profiling use cases), and `infrastructure/` / `cli.py` (CLI & I/O).
- **Alternatives considered:** Keeping procedural single-file scripts in `src/ingestion/create_manifest.py` and `src/profiling/profile_data.py`.
- **Rationale:** Procedural scripts entangle path resolution, file writing, print statements, and business logic. Clean Architecture allows unit testing core algorithms (hashing, schema validation, statistical computation) without touching disk or stdout.

### Decision: Dynamic Project Root Anchor
- **Choice:** An infrastructure module `ml_service/src/infrastructure/paths.py` that computes the workspace root dynamically by searching upward for marker files (`docker-compose.yml` or `package.json`).
- **Alternatives considered:** Relying on `Path(__file__).parents[2]` or current working directory (`os.getcwd()`).
- **Rationale:** Running python commands from the repository root (`python -m ml_service.src.cli ...`) vs running from within `ml_service/` (`python -m src.cli ...`) frequently causes `FileNotFoundError` when relative paths are hardcoded.

### Decision: Unified CLI Entrypoint (`cli.py`)
- **Choice:** A central CLI entrypoint using standard library `argparse` with subcommands: `ingest`, `profile`, and `all`.
- **Alternatives considered:** Requiring developers to execute multiple distinct script files in separate folders.
- **Rationale:** Simplifies developer onboarding and CI/CD automation to a single executable command.

## Testing Strategy

| Layer | What to Test | Approach |
| :--- | :--- | :--- |
| **Unit** | `calculate_sha256`, CSV validation, `ManifestData` serialization | Test with mock buffers / temporary test files using Python `unittest` / `pytest`. |
| **Integration** | Idempotency of `IngestionService` and manifest matching | Run against temporary directory with simulated CSV changes to verify abort on hash mismatch. |
| **E2E / CLI** | CLI subcommands `python -m src.cli ingest`, `profile`, `all` | Verify exit code 0 and existence of `manifest.json` and `data-profile.md`. |
